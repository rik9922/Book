**Product:** **Memoria** | *Your memories, made timeless.*  
**Environment:** macOS Apple Silicon, Local-First ($0 Budget)

---

## 1. Executive Summary

This independent audit assesses the genuine operational state of the Memoria repository against the product vision: a timeless, heirloom memory preservation platform spanning Fastify microservices, PostgreSQL 17 relational stores, Next.js PWA, native iOS (SwiftUI / RealityKit), and a physically realistic 3D book engine.

While foundational contracts, gRPC schemas, port registries, and initial test suites are in place, critical production paths currently rely on silent fallback mocks, hardcoded loopback IP addresses, a procedural quad-generator 3.8KB GLB placeholder, unverified media upload lifecycles, and completely missing OCR and backup/restore scripts.

## 2. Capability Matrix & Classification

Each repository capability is categorized into one of seven formal operational statuses:
1. **Implemented & Verified** — Verified with executable code, passing integration tests, and live inspection.
2. **Implemented but Not Sufficiently Verified** — Code exists but lacks full production assertions, edge-case coverage, or failure recovery.
3. **Partially Implemented** — Structure or endpoints exist, but core operational details remain stubs or partial.
4. **Mock or Test-Only Implementation** — Functional only within in-memory mock harnesses; fails or falls back in real deployment.
5. **Documentation Only** — Architecture documents describe the feature, but executable code does not exist.
6. **Missing** — Planned product capability with neither code nor documentation.
7. **Blocked** — Requires external prerequisites or manual hardware authorization.

## 3. Key Findings & Remediation Priorities

### 3.1 Eliminating Silent In-Memory Mock Fallbacks
- **Problem**: In `media-service`, `memory-service`, `identity-service`, and `book-service`, failure to connect to PostgreSQL causes an automatic downgrade to in-memory `Map` instances. If a service restarts or loses connectivity, data is silently lost.
- **Remediation**: Remove in-memory fallbacks from service runtime paths. Fail startup explicitly when `NODE_ENV !== "test"` and database connections are unavailable. In-memory mocks are strictly restricted to isolated test fixtures.

### 3.2 Resolving Database Discrepancies & Least-Privilege Roles
- **Problem**: Host runs PostgreSQL 17.10, but Docker Compose uses 16. Services connect using the `postgres` superuser.
- **Remediation**: Upgrade `docker-compose.yml` to `postgres:17-alpine`. Provision dedicated application role `memoria_app` with schema-level permissions and connection pooling.

### 3.3 Media Storage Integrity & Idempotency
- **Problem**: Media uploads accept binary chunks without validating pre-computed SHA-256 hashes against actual received payloads. Quota calculation is vulnerable to double-counting on retries.
- **Remediation**: Enforce cryptographic SHA-256 validation on upload confirmation, store original media immutably, and execute quota increments inside atomic database transactions with idempotency keys.

### 3.4 Executable Backup and Restoration Engine
- **Problem**: Backup procedures exist solely as text in documentation.
- **Remediation**: Build executable scripts (`scripts/backup.ts`, `scripts/restore.ts`) supporting logical `pg_dump` snapshots, media archive tarballs, SHA-256 manifest verification, and non-destructive dry-run restore validation.

### 3.5 Cross-Device URL Resolution & Offline Sync Queue
- **Problem**: `MemoriaAPIClient.swift` hardcodes `http://127.0.0.1:4000/api/v1`. On physical devices, `127.0.0.1` refers to the iPhone, preventing connection to the Mac development server.
- **Remediation**: Implement dynamic configuration reading `MEMORIA_API_HOST` from Info.plist/Environment with automatic fallback to Mac LAN IP or Simulator loopback. Build an offline mutation queue (IndexedDB for Web, SQLite for iOS) with sync cursors and optimistic concurrency.

### 3.6 Realistic 3D Book Engine & Blender Asset Pipeline
- **Problem**: The current GLB is a 3.8KB single-mesh cube with fake page edges.
- **Remediation**: Build a multi-component Blender authoring pipeline producing an anatomical model:
  1. Front Cover Board
  2. Back Cover Board
  3. Cambered Curved Spine
  4. Flexible Hinge Joints
  5. Text Block with micro-layered edges
  6. Individual turning page meshes with front/back UVs
  7. Silk Bookmark Ribbon
  8. PBR Materials: Fine Leather, Pebbled Leather, Bookcloth, Archival Paper, Gold Foil, and Blind Embossing.

### 3.7 Local Tesseract OCR Pipeline
- **Problem**: No OCR worker or media text extraction code exists.
- **Remediation**: Build a dedicated worker leveraging the host Tesseract 5.5.3 engine for JPEG, PNG, WebP, and multi-page PDFs, persisting extracted text with confidence scores into `media_ocr_transcripts` and indexing for full-text search.

## 4. Remediation Plan

The following implementation phases will now be executed in dependency order:
1. **Phase 1: Local Development & Infrastructure Hardening** (Postgres 17, Redis/BullMQ fail-fast, NATS durable outbox, non-superuser roles).
2. **Phase 2: Permanent Data Integrity & Backup Tooling** (Fail-fast DB connections, SHA-256 upload verification, backup & restore CLI).
3. **Phase 3: Cross-Device Foundation & Offline Sync** (LAN-aware iOS networking, SQLite local store, IndexedDB web client, sync queue).
4. **Phase 4: Photorealistic 3D Book Engine** (Blender scene pipeline, multi-part anatomical GLB/USDZ, PBR material system, page curl mechanics).
5. **Phase 5: Local Tesseract OCR Media Processing** (OCR worker, image preprocessing, PDF page extraction, PostgreSQL GIN full-text index).
6. **Phase 6 & 7: Core Application Workflows** (Archive, Bookshelf, 3D Book Studio, Admin security boundary).
7. **Phase 8: Automated Verification & Acceptance Evidence** (Integration test suites, simulator verification, performance benchmarks).
